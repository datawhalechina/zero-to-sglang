# 第 10 章 投机解码（代码实现）

普通自回归生成每次只确认一个新 token。投机解码先让草稿模型提出多个候选，再让目标模型用一次前向验证它们：候选足够准确时，一次目标调用可以确认多个 token。本章把这个过程写成一个可运行的线性草稿算法，分别处理贪心验证与保持目标分布的随机采样。

本篇对应[概念篇](./第10章_投机解码.md)，代码位于 `examples/part2/speculative.py`，复用第 3 章的模型。课程其他代码篇使用的 mini-sglang `9a91cfa` 不包含投机解码实现，因此本章的完整程序是独立教学代码；源码延伸使用真实 SGLang 的固定提交。实验默认在 CPU 上用随机小模型运行，不需要草稿权重下载，也不把目标调用次数当成实测加速比。

## 1 本章学习目标

完成本章后，你将能够：

1. 实现 draft → verify → commit 的完整循环。
2. 找到验证 logits 与草稿 token 的正确位置对应，处理额外的 bonus token。
3. 区分贪心一致性与随机采样的分布一致性。
4. 实现接受概率、拒绝后的残差分布和后续草稿丢弃。
5. 验证 EOS、最大长度、全接受、首次拒绝等边界，并说明缓存回滚和性能验证还需做什么。

## 2 运行两种解码模式

### 2.1 贪心模式

按第 3 章安装依赖后，在仓库根目录运行：

```bash
python -m examples.part2.speculative
```

目标模型使用两层随机小型 Qwen3，草稿模型使用一层。程序同时计算 target-only 贪心基线，并输出：

```text
Matches target-only greedy: True
```

随机模型之间不一定有良好的一致性，贪心接受率可能为零。这个结果说明草稿没有提供帮助，不代表验证算法错误。测试中另设 `draft = target`，用同一个模型模拟全接受分支，确认 bonus token 与调用次数的边界。

### 2.2 随机模式

```bash
python -m examples.part2.speculative --temperature 1 --draft-steps 4
python -m pytest examples/part2/tests -q -k "speculative or rejection or sampled or sampling"
```

随机模式不会宣称与相同 seed 的 target-only 输出逐 token 相等。投机算法还要抽草稿、抽接受判定、抽拒绝校正，消耗随机数的顺序不同。应当比较目标分布，而不是一条偶然的字符串。

真实模型替换时，target 和 draft 必须有相同的 token ID 含义。代码检查词表大小，但大小相同仍不足以证明 tokenizer 相同。默认实验两个模型使用同一份人工 token 约定；若自行加载两个 checkpoint，应额外检查 tokenizer 词表映射、特殊 token 和输入模板。

## 3 先把一次验证的位置算对

### 3.1 草稿来自逐步条件分布

设当前已确认前缀为 `x`，草稿长度为 `k`。草稿模型不是一次独立抽出 `k` 个 token，而是依次生成：

```text
y1 ~ q(. | x)
y2 ~ q(. | x, y1)
...
yk ~ q(. | x, y1, ..., y{k-1})
```

随机模式下必须保存每一步完整的 `q` 分布，后面才能计算接受概率和拒绝后的校正分布。`q` 指实际生成草稿时经过温度、top-k、top-p 处理后的分布；如果保存原始 softmax，却用截断分布抽样，校正公式的前提就被破坏了。

草稿每轮最多提出 `min(draft_steps, remaining_output_budget)` 个 token。草稿出现 EOS 时先停止继续提出，但这个 EOS 仍需要目标模型验证，不能看到草稿 EOS 就直接结束整个请求。

### 3.2 一次 target 前向得到多行预测

将 `x + [y1,...,yk]` 一起送进目标模型。由于因果掩码，虽然张量包含全部草稿位置，前面的预测行仍然不能看到后面的候选。

设前缀长度为 `L`，对应关系如下：

| target logits 行号 | 条件前缀 | 用途 |
| --- | --- | --- |
| `L-1` | `x` | 验证 `y1` |
| `L` | `x + y1` | 验证 `y2` |
| `L+i-2` | `x + y1 ... y{i-1}` | 验证 `yi` |
| `L+k-1` | `x + y1 ... yk` | 全接受后采样 bonus token |

因此代码取的是：

```python
verification = logits[0, len(tokens)-1:len(tokens)+len(proposals)]
```

Python 切片终点不包含在内，最终得到 `k+1` 行。最常见的偏移错误是从 `L` 开始验证 `y1`：那一行已经把 `y1` 当输入读过，预测的是下一个 token。

## 4 贪心验证：只提交连续接受的前缀

### 4.1 首次不匹配就停止

贪心模式下，用第 `i` 行 target logits 的 argmax 与草稿 `yi` 比较。相同则接受；不同则提交 target 的 argmax 作为纠正 token，然后停止验证剩余草稿。

例如草稿为 `[A,B,C]`，target 在对应条件下的贪心选择为 `[A,X,...]`，本轮提交 `[A,X]`。不能再检查并接受原来的 `C`，因为验证 `C` 的那一行条件是 `x+A+B`，真实已确认前缀却变成 `x+A+X`。

这也给出贪心一致性的归纳理由：每个已提交 token 都是目标模型在当前已确认前缀上的 argmax，因此继续下一轮时，前缀与 target-only 贪心过程一致。有限精度实现可能存在接近并列 logits 的数值差异，实际验证时仍需固定权重、后端与 tie-breaking。

### 4.2 全部接受时多取一个 token

若所有草稿都被接受，最后一行 target logits 已经给出 `x+y1+...+yk` 后的预测，可以再提交一个 bonus token，不需要额外目标调用。

一轮最多确认 `k+1` 个 token，但最大输出长度优先。如果接受草稿时已达到请求长度上限，就不再提交 bonus。若接受到 EOS 也立即结束，不能把 EOS 后的候选送给用户。

## 5 随机采样：接受与拒绝校正

### 5.1 不能照搬贪心匹配

令 `p` 为当前条件下目标分布，`q` 为草稿分布，候选 `y` 已从 `q` 抽出。接受概率为：

$$
a(y)=\min\left(1,\frac{p(y)}{q(y)}\right).
$$

因为 `y` 由 `q` 抽得，实际候选必须满足 `q(y)>0`。代码对零提议概率直接报错，避免把除零掩盖成正常数值。接受判定使用 `[0,1)` 均匀随机数与 `a(y)` 比较。

本例的 `p`、`q` 都由同一份 `probabilities` 函数计算；其温度和截断行为与第 3 章相同。公式允许不同的提议分布，但必须准确记录真实使用的 `q`。

### 5.2 拒绝后为什么不是重新从 p 抽一次

如果候选被拒绝，应从正残差归一化后的分布抽纠正 token：

$$
r(v)=\frac{\max(p(v)-q(v),0)}{\sum_u\max(p(u)-q(u),0)}.
$$

在当前这次条件分布下，候选落在 `v` 并被接受的总概率质量是 `min(p(v),q(v))`。令总接受质量为 `A`，拒绝分支概率是 `1-A`，而正残差之和恰好也是 `1-A`。最终输出质量因此为：

$$
\min(p(v),q(v))+(1-A)r(v)=p(v).
$$

这个等式解释了校正的必要性。若拒绝后直接再从 `p` 抽样，通常会重复补给已经由接受分支覆盖的概率质量，改变最终分布。

例如 `p=[0.0,0.3,0.7]`，`q=[0.5,0.5,0.0]`，接受分支只贡献 `[0.0,0.3,0.0]`，剩下 0.7 必须全部补到第三项。即使草稿从不提出第三项，正确算法也可以通过拒绝校正恢复它。

### 5.3 从单步分布到整个序列

接受草稿后，下一步的前缀仍是 target 验证过的条件，可以继续使用下一行分布。首次拒绝后提交纠正 token，丢弃剩余草稿并重新开始。这样每一步的提交分布都是对应前缀上的目标分布，才能逐步保持整个生成序列的分布。

全接受时，bonus 也必须从 target 最后一行的分布采样。不能用 draft 的下一步补上。所谓“保持目标分布”，是相对于已选定温度和截断参数后的目标采样分布；调整这些参数本身当然会改变输出分布。

数值计算中，本例用 FP32 softmax；理论分布恒等式是数学性质，不应被描述成有限精度硬件上的绝对逐位无误差保证。拒绝残差没有正质量时，代码报错而不是静默改用另一个分布。

## 6 提交边界与 KV Cache 回滚

### 6.1 本例如何隔离未接受 token

`tokens` 只保存已确认前缀，`proposals` 是本轮临时草稿。target 前向输入二者拼接，但只有 `commit` 会更新 `tokens` 和最终输出。因此拒绝后丢弃临时列表就能恢复正确条件；未接受草稿不会留在后续输入中。

这个教学版本每次重新前向完整前缀，**不维护持久化的投机 KV Cache**。这是为了让概率算法、位置对应和终止逻辑能独立验证，不是对高性能实现的描述。第 6 章已经缓存 KV，也不意味着这里可以不加处理地沿用。

### 6.2 带缓存时要恢复哪一段

真实实现可能已为全部草稿位置写入 target KV，draft 也维护自己的 KV。若只接受前 `a` 个草稿，再补一个纠正 token，必须撤销被拒绝位置及其后续候选对应的缓存引用，并让后续前向只看到已确认路径。

还要注意第 3 章的不变量：刚从 logits 采样出的纠正 token 或 bonus token，并不一定已经有可复用的 KV。纠正 token 与被拒绝草稿可能不同，不能把后者的 KV 直接保留给前者；bonus 则是刚预测出的新 token，也通常尚未前向。

实践中需同时维护已提交 token 长度、target 已缓存长度、draft 已缓存长度，以及临时验证槽位的引用关系。分页内存不能只靠切短 Python 列表就自动回收；存在在途 GPU 工作时，还需等使用结束再释放。完成这层优化后，应继续以本章无缓存算法为正确性参考。

## 7 测试与性能观察

### 7.1 三层正确性验证

第一层比较贪心结果：随机独立 draft、同模型 draft、不同草稿步数，输出都应与 target-only 基线一致。同模型实验还检查全接受情况下的目标调用次数。

第二层检查边界：零输出不调用模型；草稿 EOS 可以被拒绝；被接受的 EOS 立即结束；bonus 也可以是 EOS；不足一个草稿块的剩余输出不能超长。

第三层检查随机分布。测试用可解析的两状态 Markov 模型，初始 token 为 0，目标转移矩阵为：

$$
P=\begin{pmatrix}0.8&0.2\\0.3&0.7\end{pmatrix}.
$$

连续两个新 token 的联合分布是 `[[0.64,0.16],[0.06,0.14]]`。测试用明显不同的草稿分布做 6000 次采样，检查频率与精确值的绝对偏差不超过 0.025，同时独立检查残差恒等式。这是回归检验，不能代替上一节的数学论证。

### 7.2 怎样解释程序计数

| 计数 | 含义 | 不能据此直接推断什么 |
| --- | --- | --- |
| `target_calls` | 目标前向次数 | 目标模型总耗时 |
| `draft_calls` | 草稿前向次数 | 草稿开销可以忽略 |
| `accepted / proposed` | 接受的草稿数量 / 提出的草稿数量 | 整体加速比；分母还包含拒绝后未逐个验证的草稿 |
| `rounds` | 每轮草稿、接受数与是否拒绝 | 用户感知的流式到达时间 |

可以把性能问题拆成“平均每轮确认多少 token”和“每轮付出多少时间”。后者包含草稿执行、目标块验证、采样、缓存管理及同步。草稿块变长可能增加一次验证收益，也可能引入更多无效草稿、显存压力和计算开销。随机小模型实验只验证算法，不适合得出 GPU 加速结论。

要测真实收益，应在同硬件、同模型、同请求集、同采样参数下，对比预热后的端到端延迟、输出吞吐和尾延迟；计时需要正确处理 GPU 异步执行，并报告接受率、draft 配置与额外显存。

## 8 连接真实 SGLang 源码

本节固定使用 SGLang [1291f317](https://github.com/sgl-project/sglang/tree/1291f3175d3b7614821884e9653985fcd3c3dae8)，而不是暗示 mini-sglang 已有同名模块。先看 `python/sglang/srt/speculative/standalone_worker_v2.py`：`StandaloneDraftWorker` 为独立草稿模型保留自己的 embedding 和 LM Head，`StandaloneWorkerV2` 检查 target/draft 的词表兼容性，再接入共享执行流程。

随后阅读 `eagle_worker_v2.py` 中的执行组织与 `eagle_info.py` 中的验证、草稿输入结构，观察系统怎样传递候选 token、检索索引、注意力元数据和缓存信息。独立草稿复用了部分基础设施，不代表本章线性算法等同于 EAGLE。

| 本章实现 | 真实系统继续需要处理的内容 |
| --- | --- |
| 一条线性草稿 | 树状候选、不同草稿算法与专用输入元数据 |
| 全前缀重算 | 增量 KV、临时槽位、接受路径收集与资源回收 |
| 单请求、单设备 | batch 内不同接受长度、多 rank 一致性、与调度器交互 |
| Python 概率处理 | 向量化采样内核、同步开销与流式结果提交 |

SGLang 官方文档还列出 EAGLE、MTP、独立草稿等不同入口。阅读或运行时应使用与安装版本对应的文档；本章不预设任意两个模型都能直接组成有效的草稿与目标组合。

## 9 总结与测试题

### 9.1 课程总结

投机解码把“提出候选”和“确认输出”分开。因果 target 前向一次提供多个条件分布；贪心模式在首次不匹配时纠正，随机模式用接受概率与正残差分布保持目标采样语义。位置对齐、首次拒绝、EOS 和 bonus 边界都处理正确之后，才适合继续做缓存与内核优化。

### 9.2 测试题

1. 当前前缀长 5、草稿长 3 时，验证三个草稿和采样 bonus 分别使用哪些 logits 行？
2. 为什么首次拒绝后，后面的草稿即使“看起来正确”也不能直接接受？
3. 给定 `p=[0.4,0.6]`、`q=[0.8,0.2]`，两个候选各自的接受概率是什么？拒绝后从什么分布抽样？
4. 为什么 target 与 draft 的词表大小相等，仍不足以保证二者兼容？
5. 若已写入所有草稿 KV，但只接受前两个，纠正 token 与未接受 KV 分别应该怎样处理？
